# MiniMax H3 · 8 GB 笔记本调优笔记

> 整理时间：2026-11-22。本机实测 + 社区同配置实测对照，每条结论都标了出处。
> 本机：RTX 5070 Laptop 8 GB（sm_120）· 31.2 GB RAM · torch 2.12.1+cu130 · Python 3.13.12 · ComfyUI 0.42.1

## 0. 最值钱的五条（先看这个）

| # | 结论 | 出处 |
|---|---|---|
| 1 | **分辨率短边不能超过 768**。3:4 画幅下 `megapixels` 该填 **0.75**（=768×1024）；填 0.9 会得到 832×1120、填 1.0 得到 896×1184，**短边超出训练区间，画质反而变差** | [8GB 工作流](https://github.com/FlowForgeLabAi/MiniMax-H3-8GB-Workflows) §4 |
| 2 | **sm_120 上 SageAttention 是负优化**：同一几何下 kitchen INT8 22.8 ms / 误差 0.0164，Sage 29.0 ms / 0.0387（慢 1.27×、误差 2.4×）；而且这个 patch 会**绕过 `optimized_attention`**，让 `ModelAttentionBackend` 失效 | [8GB 陷阱](https://github.com/FlowForgeLabAi/-h3-8gb-traps) §2 |
| 3 | **turbo LoRA 对 pruned 基座只有 80.3% 生效**（208/259 个模块，51 个 `adaln_proj` 因维度 8 vs 2688 被跳过）。控制台反复刷 `shape ... invalid for input of size ...` 不是进度，是逐层失败 | 同上 §4 |
| 4 | **8 步和 20 步构图基本一致**，时间只有 1/2.5；20 步留给最终成片 | 同上 §6 / [8GB 工作流](https://github.com/FlowForgeLabAi/MiniMax-H3-8GB-Workflows) |
| 5 | **真正的墙是内存不是显存**：刚重启时 0.9–6 s/block，连续跑 1.7 小时后 212 s/block。判断方法看 `nvidia-smi` **功耗**——健康 64–98 W，掉到 **34–36 W 平线**而利用率仍 99% 就是换页了，**每次开跑前重启 ComfyUI** | 同上 §5 |

## 1. 提示词：动作不跟随的根因在这里

社区实测（[8GB 陷阱](https://github.com/FlowForgeLabAi/-h3-8gb-traps) §1、[人物替换教程](https://github.com/lshhhhhhh/ai-school-op)）反复提到同一件事：**短的自然语言提示词会被模型"照抄/忽略"，必须用官方结构化格式**。

官方 Ref2VA 六段（全英文）：

```text
subject_definitions: <Subject 1> is the person in <Picture 1>, whose identity, face, hair,
  body shape and clothing define the character in the target video. ...
summary: [video generation + reference] ...
retention_analysis: ...
detailed_description: [Shot 1] ... [Shot 2] At 00:06.000, the camera cuts to ...
overall_soundscape: ...
non_diegetic_music: ...
```

**三条最容易踩的坑（都有复现）：**

1. **时间轴没铺满**：10 秒的片子只写 `[Shot 1]` → 后段没有内容可描述，模型自己填空景，**主体消失**（实测 ~7 s 处人物没了）
2. **运镜没有落点**：只写「小幅度慢速推近」→ 模型不知道停在哪，**一路推过头把主体推出画面**。必须写 `toward <具体落点>, and comes to rest at a medium shot`
3. **自相矛盾**：既要求「保持整体构图不变」又要求「推镜」——构图必然变，模型只能选一个

> 我们 15 秒那版末尾人物转身背对镜头，很可能就是第 1 条的变体：提示词按时间写了五段，但描述的是"动作清单"而不是"镜头覆盖"，模型到后段没约束就自由发挥。

## 2. 推荐配方

| 场景 | 分辨率 | 步数 | sampler | scheduler | LoRA | 强度 | 参考耗时 |
|---|---|---|---|---|---|---|---|
| 5 s 抽卡 | 768×1024（0.75 MP @3:4） | 8 | `euler` 或 `dpmpp_sde` | `beta` | turbo | 1.0 | 6–15 分钟 |
| 5 s 抽卡（快） | 768×1024 | 4 | `euler` | `simple` | turbo | 1.0 | ~9 分钟 |
| 成片 | 768×1024 | 20 | `res_multistep` | `simple` | 无 | — | 34–44 分钟（10 s） |
| 15 s 成片 | 768×1024 | 8–20 | 同上 | 同上 | 同上 | 同上 | 约为 5 s 的 3–4 倍 |

本机实测对照（8 步 / 832×1120 / turbo 1.0 / dpmpp_sde+beta）：**11–19 分钟一条 5 s**，比社区同配置略慢，与超了 768 短边（像素 +18%）相符。

## 3. 注意力后端：别再用 Sage 节点

社区实测（sm_120，H3 真实几何 heads=56/head_dim=128/S=8192/bf16）：

| 后端 | 耗时 | 相对误差 |
|---|---|---|
| SDPA bf16（什么都不加） | 143.1 ms | 0.0025 |
| **comfy-kitchen INT8** | **22.8 ms** | **0.0164** |
| kitchen INT8 + head_chunks=10 | 26.2 ms | 0.0164 |
| KJ SageAttention（sm89 kernel） | 29.0 ms | 0.0387 |
| sage + head_chunks=10 | 31.6 ms | 0.0387 |

**做法**：摘掉 `MiniMaxH3MemoryEfficientSageAttentionPatch`，改用内置节点 `ModelAttentionBackend = "comfy kitchen attention"`（命令行等价 `--use-ck-attention`）。

> 注意：Kitchen 的 CUDA 后端要求 **cu130+**，我们满足。
> `MiniMaxLowVRAMAttention` 与 sage patch 不冲突，`head_chunks` 走 `transformer_options`；
> 实测 `head_chunks=10` 与不分块**误差完全一致**，只是慢 15% —— 显存够时可以设小。

## 4. LoRA 怎么选（社区横评）

| LoRA | 结论 | 出处 |
|---|---|---|
| `ref2v_turbo_4step_v0.1`（OG） | 细节最多，但快动作会糊 | [Kijai #60](https://huggingface.co/Kijai/MiniMax-H3-experimental/discussions/60) |
| `DMAD_4step_rank39` | 综合最好（社区 #1） | 同上 |
| `ref2v_turbo_8step_v1.1` | 更稳但更平 | lightx2v 仓库 |
| `fl2v` turbo 用在 ref2v 工作流 | 比 ref2v 专用 LoRA 更清晰（ref2v LoRA 糊手） | [lightx2v #33](https://huggingface.co/lightx2v/Minimax-h3-Turbo/discussions/33) |
| `turbo_v4_step600`（原工作流那支） | 官方推荐参数：**8 步 / euler / beta / 强度 1.0 / sigma shift 12** | [drbaph](https://huggingface.co/drbaph/MiniMax-H3-Turbo-Lora-ComfyUI) |

**没有一支 turbo 能追平原生 20 步**：中文实测（[benchmark](https://github.com/fengyungithub/dsh-short-video-studio/blob/main/docs/minimax-h3-video-benchmark.md)）lightx2v 8 步帧锐度 5.630 vs 20 步 7.243（−22.3%）。

## 6. 排错速查

| 现象 | 原因 | 处理 |
|---|---|---|
| `sageattention is not new enough ... NoneType` | 没装 / 轮子 ABI 不匹配 | 装匹配 torch 的 2.2.0 wheel + triton-windows，重启 |
| `缺失节点 easy cleanGpuUsed` | Easy-Use 没装或没加载 | clone 到 custom_nodes + 装 requirements + 重启 |
| 出片越来越慢、GPU 功耗平在 34–36 W | 内存换页 | **重启 ComfyUI**；可加 `--disable-pinned-memory` |
| `avcodec_open2 libx264 ... EINVAL` | 视频宽高是奇数（yuv420p 要求偶数） | 换 `VHS_VideoCombine`（crf 12≈视觉无损）或把尺寸取偶 |
| 后段人物消失 / 主体被推出画面 | 提示词时间轴没覆盖 / 运镜没落点 | 补 `[Shot N] At 00:0S.SSS ...` 与落点 |
| 构图不听话（要全身给半身） | 8 步蒸馏模型对构图约束弱 | 写进 `detailed_description` 的镜头句，或降靠 20 步 |
| 控制台刷 `shape ... invalid for input` | pruned 基座与 LoRA 的 AdaLN 维度不一致 | 正常现象（80.3% 生效），不影响出片 |

## 11. 本机实测补充（2026-11-22 晚间）

### VHS 的 crf 在纯 API 提交里能用（关键发现）

`VHS_VideoCombine` 的 `crf` / `pix_fmt` / `save_metadata` / `trim_to_audio` **不出现在 `/object_info`**（它们挂在 `format` 这个动态下拉底下），但**可以直接作为扁平的节点 inputs 字段写进 API 工作流**，ComfyUI 不拒绝、也会真正传给 ffmpeg：

| 配置 | 码率 | 5 秒文件 |
|---|---|---|
| 不给 crf（默认） | 2559 kbps | 1.58 MB |
| `"crf": 12, "pix_fmt": "yuv420p"` | **7259 kbps** | **4.47 MB** |

模板 `minimax-h3-ref2v-community` 已固化 crf=12，并在 schema 里露出 `crf` 变量。

### 社区配方（kitchen 后端）在本机的实测

| | 结果 |
|---|---|
| 5 秒 / 124 帧 / 768×1024 / 8 步 | **冷态 4.9 分钟，热态约 2 分钟** |
| 对照：旧模板 832×1120 + Sage patch + SaveVideo | 10–12 分钟 |
| 构图 | 唯一稳定给**全身**的版本 |

结论：去掉 Sage patch 换 kitchen 后端 + 短边压到 768 + VHS 输出，是**又快又好看**的组合，已设为默认模板。

### 踩坑记录

- 插件把 `/object_info` 缓存在进程内，**ComfyUI 重启后不刷新**；新增自定义节点后必须重载插件 bundle（`set_bundle` 关→开），否则 `comfyui_run` 会误报"缺节点"。
- 工具等待上限 30 分钟，超时后任务被标 `unknown` 且**不会自动归档产物**；产物只在 ComfyUI 自己的 `output/` 里，需要 `comfyui_run { promptId }` 补收。
- 磁盘：E: 只剩 ~11 GB，D: 有 196 GB。再加模型建议放 D: 并做 junction。

## 12. Sol-Attn 试装结论（2026-11-22 晚）：**不可用，已禁用**

- 装上后启动正常，日志确认 `SM120 → flex_attention` 路径、注入成功
- **但第一次 `torch.compile` 时直接把 ComfyUI 进程打崩**（日志停在 `sol_attn_flex 加载成功` 之后，无异常输出）
